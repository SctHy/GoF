# 混合负载基准与瓶颈定位

`scripts/bench_mixed.py` 用真实 HTTP、MySQL、Redis 和 RabbitMQ 验证 Feed / 视频读取与点赞事务同时运行时的表现。基准只连接本地 `127.0.0.1:18080`，不清空数据库、缓存或队列。结果不是生产容量承诺，也不与旧的 200 次纯读短样本作性能提升比较。

## 复现

先按 [development.md](development.md) 启动 API、Worker 和依赖服务，再执行：

```bash
# 第一次准备 author + 4 个 reader，并由 author 真正上传视频和封面。
python3 scripts/bench_mixed.py --prepare-only
# 顺序运行均匀访问和单视频热点，各预热 5 秒、采样 30 秒。
python3 scripts/bench_mixed.py --concurrency 8 --warmup 5 --seconds 30 \
  --videos 24 --seed 1729 --output .local/mixed-benchmark
```

账号会话和上传地址保存在 `.local/mixed-sessions.json`，文件权限为 `600`，不可提交或分享。重复运行复用这些账号；默认访问令牌 15 分钟过期，过期会在准备阶段以 `401` 失败。删除本脚本的会话缓存，或用 `--sessions .local/mixed-sessions-new.json` 指定新路径重新准备，会创建新账号；不会删除旧账号。注册受到正常 IP 限流，遇到 `429` 会等待 61 秒，最多重试两次；不要同时运行其他批量注册验收。脚本不绕过认证、上传归属校验或限流。

每次新建 24 个视频，共用该 author 拥有的上传资源。结束后经作者 API 软删除本次视频；账号、上传文件、已完成事件及互动历史保留。异常中断时 `.local/mixed-benchmark/fixture-ids.json` 留有本次视频 ID，可用缓存中的 author 会话经 API 清理。不要截断业务表。

原始证据在输出目录的 `result.json` 及逐时点的 `*.prom`。JSON 包含每类请求数量、成功率、P50/P95/P99、错误分类、采样实际耗时、CPU、数据库样本量、EXPLAIN、Outbox 和计数对账。分位数采用 nearest-rank，包含失败请求耗时；预热单独记录，不计入正式吞吐。

## 负载与计时口径

默认 8 个 Python 线程闭环请求：每个线程收到上一请求结果后发下一请求，不设目标 RPS。`urllib` 每次建立 HTTP 连接，HTTP 连接开销和客户端解析均进入端到端耗时。

- 4 个 reader 各自只有一个写线程，循环执行 3 次 Feed、3 次视频详情，再顺序点赞/取消，避免同一用户并发写制造无意义锁竞争。
- 另外 4 个线程只做 Feed / 视频读取，复用 reader 的认证，但不写互动状态。可用 `--concurrency 4` 测全部为混合线程，最大允许 64；写线程始终最多 4 个。
- 均匀场景按固定种子从 24 个视频随机取一个；热点场景的详情和互动都固定到同一个视频，Feed 仍为真实时间线首页。
- 写线程的循环是 75% 读、25% 写，但混合线程与纯读线程速度不同，所以整体读写占比必须从请求计数计算，不能直接宣称固定比例。
- 到达采样截止时间后，完成当前循环，确保点赞/取消成对收尾。报告实际耗时，因此可能略长于 30 秒；不会把尾部请求算进分子却忽略尾部时间。

每 5 秒采集 API / Worker Prometheus 原文和数据库 Outbox、InnoDB 锁等待累计值，采集自身会带来少量额外开销。macOS 下也用 `ps` 记录 API / Worker 的累计 CPU 时间及 RSS；CPU 时间增量除以时间差表示平均占用多少个 CPU 核。Python 的 `process_time` 记录负载发生器 CPU，不包含 MySQL / Redis / RabbitMQ 容器。其他并行测试也会污染全局计数，应在没有其他压测时复现。

热点选择本次最后发布的视频，正式压测前验证它出现在 20 条 Feed 首页中。否则热点被排在首页之外，会让两场景承担不同的统计缓存失效成本，造成误导。

需要定位具体锁对象时附加 `--lock-samples`。它通过专属 Compose 的本地 MySQL root 账号只读查询 `performance_schema.data_lock_waits` / `data_locks`，记录等待表、索引、锁模式及瞬时数量，不修改权限或仪表配置，不采集 SQL 正文或业务 payload。五秒一次的瞬时采样可能漏掉短等待，不能用采样占比推算锁等待时间占比。

每场结束按本次视频比较 `video_stat.like_count` 与有效 LIKE 事实，要求全部相等且归零。随后最多等待 120 秒，要求本次视频的 Outbox pending 和 failed 都为零。Outbox 投递完毕代表已被 Broker 确认，不等同于所有消费者投影完成或 RabbitMQ 队列完全为空；消费者成功/失败通过同时保存的 Worker 指标观察。

### 已定位的限制

1. **互动事务出现真实锁等待，热点写尾延迟明显变长。** 两场 InnoDB 全局锁等待分别增加 3,891 / 3,172 次，累计等待时间增加 21.243 / 32.979 秒。这里是多个事务等待的累加，不能当成整个采样停顿时长。均匀场景多次捕获 `interaction_action.PRIMARY` 上 `X,INSERT_INTENTION` 等待；热点既捕获该等待，也捕获 `video_stat.PRIMARY` 的 `X,REC_NOT_GAP` 等待。因此不能把所有延迟笼统归到视频统计行。
2. **证据对应到具体事务路径。** [CommitAction](../apps/api/internal/infra/persistence/interaction/durable.go) 每次先对互动事实执行 `INSERT ... ON DUPLICATE KEY UPDATE`，再按用户/视频/动作唯一键锁定行，再更新视频统计并写 Outbox。下一步优先评估缩短事务持锁时间和减少重复 upsert；保留原有并发建行、幂等和计数一致性约束。此次只定位，没有修改该事务，也没有声称优化收益。代码会对 MySQL 1213 / 1205 最多尝试三次，零 HTTP 错误不能证明没有数据库内部重试；当前没有分步骤耗时或重试次数指标，尚不能精确分摊成本。
3. **不是已经观测到的连接池耗尽或发生器 CPU 饱和。** API 池采样最多 8 条连接、Worker 最多 6 条，上限各 50，等待次数/等待时长增量均为零。均匀 / 热点期间 Python 平均占用约 0.30 / 0.29 核，API 约 0.74 / 0.67 核，Worker 约 0.18 / 0.15 核。API 自身 histogram 的平均点赞处理耗时约 30.12 / 44.45 ms，与写路径变慢一致；它是均值，不能与客户端 P99 直接相减。未采集 MySQL 的 CPU / IO profile，不能据此排除容器资源或磁盘的影响，也不应先调大连接池。
4. **本轮没有证据要求新增索引。** 结束时 EXPLAIN 显示时间线使用 `idx_status_published`、反向索引扫描，预估 24 行；互动使用 `uk_user_video_type`，统计使用主键，后两者均为 `const`、预估 1 行。Feed 页缓存命中约 99.70% / 99.75%，卡片命中 100%，统计缓存命中约 94.73% / 96.97%。小数据下的计划与热缓存结果不能替代大表查询计划及冷启动实验。

`.local/mixed-benchmark` 和 `.local/mixed-lock-diagnostic` 是前两轮诊断记录。它们曾将热点设为最早发布的视频，落在 20 条首页之外；修正后选择最新视频，并加了首页包含性检查。本页只引用修正后的最后一轮；前轮保留便于审计，不把不同夹具或增长的历史表数据之间的差异当成 A/B 性能提升。

## 局限和下一步

这是 24 个新视频、4 个活跃写用户、单机开发环境的功能性负载基准。历史软删除数据与事件仍影响表大小，具体总量以结果 JSON 为准。场景间复用视频和账号，先均匀后热点，会受缓存和历史数据增长影响；没有随机交叉顺序、多轮置信区间，也没有做百万级数据、远程网络、真实视频流量或上传转码并发实验。

闭环负载在服务变慢时会自动降低到达率，可能掩盖排队恶化，不能用于生产 SLO 或最大容量结论。Python 客户端也可能先占满一个 CPU 核。扩容前先用独立负载机、连接复用、固定到达率和足够数据量重复测量，再根据服务 CPU、数据库等待与队列增长决定优化方向。

同一视频的计数更新集中在一条 `video_stat` 行，是明确存在的串行临界区，但是否已成为本次瓶颈必须结合热点延迟和锁等待增量判断。不能因为代码中有行锁，就直接声称需要分库分表或改成异步计数。
